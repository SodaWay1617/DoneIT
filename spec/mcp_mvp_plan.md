# DoneIt — план MCP MVP на Spring AI

Дата: 27 октября 2026. Статус: MVP реализован и проверен локально; развёртывание на VPS отдельно.

## 1. Цель и принятые границы

Агент на ноутбуке получает доступ к обычным задачам DoneIt на VPS через MCP по HTTP. Сервер использует Spring AI внутри существующего приложения, существующую PostgreSQL и прикладные сервисы DoneIt.

MVP обеспечивает создание, поиск, чтение, изменение и логическое удаление одной задачи за вызов. Под удалением понимается существующее закрытие в `CLOSED`: физическое удаление задач запрещено правилами проекта. Инструмент называется `close_task`, чтобы его поведение было очевидным.

В MVP не входят:

- CRUD регулярных задач и изменение их расписаний;
- управление проектами, пользователями, участниками и исполнителями;
- отдельное управление справочником тегов;
- списание времени, массовые операции и автоматическая декомпозиция;
- аналитика, прогноз оценок, отчёты и собственные вызовы LLM;
- OAuth, UI управления ключами, серверный интерфейс согласования массовых изменений;
- настройка HTTPS и изменения пользовательского интерфейса.

Существующие теги и исполнители задачи должны сохраняться даже тогда, когда MVP не позволяет их редактировать. Создание задачи во входящих по умолчанию: `NEW`, проект MAIN текущего пользователя, `priority=NONE`, `planningType=REQUIRED`, без выдуманной даты, времени или оценки.

## 2. Техническое решение

```text
Агент / MCP-клиент на ноутбуке
    → HTTP Streamable MCP напрямую на VPS
    → Spring Security: Bearer-токен → пользователь DoneIt
    → MCP tools → application services
    → существующие repositories / PostgreSQL
```

- Остаёмся на Java 21, Spring Boot 3.5.x и Spring MVC.
- Используем Spring AI 1.1.8, BOM и `spring-ai-starter-mcp-server-webmvc` (MCP SDK 0.18.3).
- Явно задаём `spring.ai.mcp.server.protocol=STREAMABLE`, путь `/mcp`, первоначально синхронный режим.
- MCP отделяется небольшим модулем `com.doneit.mcp` с web/security, application и DTO. Бизнес-правила задач остаются в существующих модулях.
- Публикуем только согласованные инструменты. Отключаем ненужные resources, prompts, completion и уведомления. Проверяем, что автоматическое сканирование не выставляет другие beans как инструменты.
- Интеграция выключена по умолчанию. Если её включили без корректной конфигурации авторизации, доступ не должен открываться.
- MCP не требует модели, API-ключа LLM, нового микросервиса, БД или отдельного Docker-образа.

## 3. HTTP и минимальная защита

HTTP — транспорт MVP; HTTPS будет отдельной задачей. Пользователь явно выбрал временный прямой HTTP-доступ на полдня, без SSH-туннеля. Это решение заменяет исходную рекомендацию туннеля. Обязателен конечный срок действия токена; по истечении сервер отклоняет запросы.

Пример предполагаемого подключения:

```text
MCP-клиент → http://VPS_IP:8080/mcp → DoneIt
```

MCP работает на том же HTTP-порту приложения, маршрут `/mcp` защищён отдельной security chain. В allowlist Host нужно добавить фактический IP/домен подключения. Не переносим всё приложение на loopback и не ломаем доступ к UI. Новый контейнер не нужен. Подключение к VPS и deploy по-прежнему требуют отдельного поручения.

Прямой HTTP не шифрует токен и содержимое задач. Хеш на сервере и срок действия не заменяют шифрование; временный риск принят пользователем. HTTPS остаётся за пределами данного этапа.

Минимальные требования:

1. Случайный токен высокой энтропии, например 32 случайных байта; передача только в `Authorization: Bearer ...`.
2. Исходный токен хранится у клиента, SHA-256 хеш — на сервере, вне Git и исходного кода. Отдельная конфигурационная запись: `tokenId`, пользователь, хеш, разрешение чтения/записи, срок действия. Один клиент может иметь свой токен; общего семейного суперключа нет.
3. Токен проверяется на каждом HTTP-запросе MCP. Предусмотреть отзыв/ротацию через конфигурацию, в MVP допустим перезапуск приложения. Сравнение хеша — без обычного раннего выхода по отличающемуся байту.
4. Пользователь определяется токеном. Параметр `userId` или username от агента не даёт дополнительных прав. Используем существующие ограничения видимости и доступа к проектам/задачам.
5. Отдельная Spring Security chain для реальных MCP-маршрутов: без form-login/remember-me и редиректов на `/login`. Ошибка авторизации возвращается как 401/403. Не ослабляем цепочку веб-интерфейса.
6. CSRF браузерных форм остаётся включён. Исключение допускается только для MCP-маршрутов с обязательной Bearer-авторизацией; cookies сами по себе не авторизуют MCP.
7. Если транспорт использует session ID, он не заменяет авторизацию и не должен позволять пользоваться чужой сессией. Проверить привязку сессии к пользователю в выбранном SDK.
8. Проверяем допустимые Host/Origin; отсутствие Origin у небраузерного клиента не является ошибкой само по себе. Не разрешаем произвольные браузерные origins и не доверяем forwarded-заголовкам от любого адреса.
9. Ограничиваем размер запроса, частоту вызовов, длину строк и размер выдачи. Токены и Authorization не попадают в логи или ответы инструментов.

Статический Bearer-токен — выбранная упрощённая авторизация для контролируемого MCP-клиента, умеющего задавать HTTP-заголовок. Не выдаём её за полноценный OAuth-процесс подключения любого MCP-клиента.

## 4. Инструменты MVP

| Инструмент | Назначение | Основной контракт |
|---|---|---|
| `list_projects` | Выбрать доступный проект | Только доступные проекты: ID, название, MAIN |
| `list_tasks` | Поиск и список | Текст, projectId, статусы, диапазон плановых дат; пагинация |
| `get_task` | Прочитать одну задачу | ID → карточка и маркер актуальности |
| `create_task` | Создать обычную задачу | Поля создания, уникальный `requestId` |
| `update_task` | Изменить отдельные поля | ID, ожидаемая ревизия/updatedAt, набор изменений |
| `close_task` | Закрыть без удаления | ID, ожидаемая ревизия/updatedAt → CLOSED |

`list_projects` — вспомогательное чтение, не CRUD проектов. Все инструменты работают в рамках пользователя токена.

### Поля и ответы

- Карточка: ID/код, название, описание, проект, статус, приоритет, planningType, плановая дата или дата-время, дедлайн, оценка, фактические минуты (только чтение), доступные метаданные тегов/исполнителей, updatedAt.
- В первой версии разрешаем изменять название, описание, проект, статус, приоритет, planningType, планирование, дедлайн и оценку. Теги, исполнители и фактическое время через MCP пока не редактируются, но обязательно сохраняются.
- Для полного интервала возвращаем и сохраняем существующий `endTime`; изменение связанного времени/оценки следует текущим правилам `TaskInterval`. Неподдерживаемую комбинацию отклоняем, не исправляем молча.
- `update_task` имеет семантику PATCH: отсутствующее поле сохраняется; явное очищение разрешено только для nullable-полей. Различаем отсутствие, `null`, пустую строку и ноль. Запрещаем неизвестные поля.
- Поскольку текущий `EditTaskCommand` содержит полное состояние, адаптер читает доступную текущую задачу, объединяет только разрешённые изменения и передаёт полный согласованный command существующему сервису. Нельзя подставлять нули/пустые значения вместо пропущенных полей.
- Даты принимаем в ISO-формате; timezone приложения сообщаем клиенту в описании инструмента/контракте. «Завтра» и «следующая суббота» агент сначала переводит в конкретную дату. Не используем часы ноутбука как источник истины.
- Поиск возвращает ограниченную страницу, например 20 задач по умолчанию, максимум 100; детерминированный порядок и признак следующей страницы. По умолчанию ищем незавершённые задачи; DONE/CLOSED доступны явным фильтром.
- Ответ на запись содержит фактически сохранённую карточку и перечень изменений. Ошибки имеют стабильные коды: `VALIDATION_ERROR`, `NOT_FOUND`, `CONFLICT`, `FORBIDDEN`, без внутренних stack traces и утечки чужих данных.
- Нельзя передать ID регулярки вместо обычной задачи: инструменты и DTO явно относятся к обычным задачам; они не вызывают сервисы регулярных задач.

## 5. Согласие пользователя и целостность изменений

- Чтение не требует дополнительных подтверждений после авторизации.
- Создание и обновление выполняются по явному поручению пользователя; клиент показывает планируемые изменения перед вызовом, если это предусмотрено его режимом работы.
- Закрытие помечается как изменяющее и потенциально разрушительное действие; выбранный клиент должен уметь запрашивать согласие пользователя на него.
- MCP-аннотации readOnly/destructive — подсказки клиенту, а не серверная система разрешений. `confirmed=true`, присланное агентом, не доказывает согласие человека. В MVP доверяем проверенному клиентскому процессу подтверждения; при его отсутствии токен оставляем read-only. Серверное согласование через DoneIt — отдельный следующий этап.
- Массовых операций и инструментов физического удаления нет.
- Повтор `create_task` с тем же `requestId` и тем же содержимым возвращает исходный результат, а не создаёт дубль. Повтор с другим содержимым даёт конфликт. Ключ ограничен пользователем и клиентом; запись дедупликации и создание задачи атомарны.
- Обновление/закрытие проверяет ожидаемую актуальность задачи в той же транзакции, что и запись: условный UPDATE или блокировка строки и повторная проверка. Простого сравнения до начала записи недостаточно. Если используем `updatedAt`, проверяем точность PostgreSQL и все пути его обновления; при недостаточности вводим явную ревизию через Liquibase.
- При ошибке откатываем задачу целиком. Изменение проекта, планирования и статуса не должно оставлять частично сохранённое состояние.

## 6. Аудит

Текущая `task_change_history` пишет через DB-триггеры планирование, статус, оценку и дедлайн. Она не покрывает создание, название/описание и источник действия, поэтому одной этой таблицы для аудита MCP недостаточно.

Добавляем небольшой журнал MCP-операций через Liquibase:

- время, пользователь, `tokenId`/clientId, имя инструмента, requestId;
- задача при наличии, результат и код ошибки;
- для успешной записи — изменённые поля и необходимые значения до/после;
- для чтения — метаданные вызова, без копирования полного списка задач в журнал.

Успешные изменения и их аудит сохраняются в одной транзакции. Неуспешный вызов логируется после отката так, чтобы аудит не исчез вместе с отменённой транзакцией. Исходный токен, HTTP-заголовки авторизации и секреты не записываем. UI истории задач продолжает работать как прежде. Не включаем подробный HTTP body logging; ротация файловых логов обязательна, чтобы не расходовать диск бесконтрольно.

## 7. Последовательность работ

### Шаг 1. Контракт и проверка совместимости

- Выбрать MCP-клиент на ноутбуке и проверить его поддержку Streamable HTTP, Bearer-заголовка и подтверждения записи.
- Зафиксировать версию Spring AI 1.1.x и совместимую версию протокола; не обновлять Boot до 4.x ради этого этапа.
- Утвердить DTO и семантику поиска, PATCH, закрытия, повторной отправки и конфликтов.
- Проверить конфигурацию доступа на VPS чтением конфигов только в рамках отдельного разрешения на доступ к VPS; этот план сам по себе не разрешает подключение или deploy.

Результат: согласованный список инструментов, пример конфигурации клиента без секретов и понятная схема HTTP-доступа.

### Шаг 2. Каркас MCP и авторизация

- Подключить BOM/starter, конфигурацию и переключатель включения.
- Реализовать отдельную security chain и проверку конфигурационных токенов.
- Довести идентичность пользователя до исполнения tools. Отдельно проверить перенос SecurityContext через внутренние потоки SDK: наличие principal в HTTP-фильтре не гарантирует его наличие в tool handler.
- Обеспечить очистку контекста после каждого вызова, изоляцию параллельных пользователей, проверку прав при каждом обращении и отсутствие случайной публикации tools.

Результат: защищённое соединение и `tools/list`, пока без возможности менять задачи.

### Шаг 3. Чтение

- Реализовать `list_projects`, `list_tasks`, `get_task`.
- Переиспользовать существующие проверки видимости; добавить только необходимые параметризованные read-запросы и DTO.
- Проверить проекты, личные/общие задачи, скрытые задачи, пагинацию и даты.

Результат: read-only MVP, который уже можно подключить с ноутбука.

### Шаг 4. Запись и аудит

- Добавить миграцию журнала MCP и хранения ключей идемпотентности.
- Реализовать `create_task`, затем `update_task`, затем `close_task` через существующие сервисы.
- Добавить PATCH-адаптер, проверку актуальности, дедупликацию создания и аудит.
- Сохранить ограничения MAIN, участников, статусов, интервалов, личных тегов и разделения планирования/дедлайна. Вызовы не обходят прикладные сервисы прямыми CRUD-запросами.

Результат: CRUD одной обычной задачи с контролем прав, повторов и конфликтов.

### Шаг 5. Проверки

- Unit-тесты: токен/срок/режим read-only, валидация DTO, слияние PATCH, ошибки и конфликты.
- MCP-протокол: initialize, tools/list, tools/call и бизнес-ошибки; тестируем реальный контракт, а не только прямой вызов Java-метода.
- PostgreSQL: создание, обновление, закрытие, аудит/откат, параллельный PATCH, повтор одного requestId и конкурирующее создание с одним ключом.
- Безопасность: нет/неверный/отозванный токен, подмена пользователя, чужая задача/проект, чужая MCP-сессия при наличии, Origin, read-only токен, размер запроса, отсутствие секретов в логах.
- Регрессия веб-интерфейса: вход/remember-me/CSRF, создание и редактирование задач, история, статусы и проекты.
- Сквозной сценарий с ноутбука: найти проект → создать NEW → прочитать → изменить название/дату → закрыть → проверить результат в UI и аудите.

Результат: подтверждённая работоспособность с реальным выбранным MCP-клиентом.

### Шаг 6. Подключение и документация

- Подготовить пример настроек прямого HTTP, выдачу/замену токена с конечным сроком действия, проверку доступности, отключение MCP и откат.
- После отдельного поручения на VPS: резервная копия перед миграциями, одна сборка релиза, применение миграций и smoke-тест. Не пересобирать образы ради каждой локальной проверки.
- Проверить, что публичный `/mcp` требует действующий Bearer-токен и правильный Host/Origin, а UI продолжает работать.
- Настройку HTTPS и OAuth оставить самостоятельными этапами.

Результат: агент на ноутбуке работает с задачами VPS напрямую по HTTP с Bearer-авторизацией.

## 8. Работа с Docker и диском

- Планирование, чтение кода, DTO, unit-тесты, проверка конфигурации и часть протокольных тестов — без Docker.
- Не создавать отдельный образ для MCP. Разработка в существующем приложении, обычная JVM/JAR.
- DB-проверки объединять в осмысленные прогоны, избегать повторного скачивания уже имеющихся PostgreSQL-образов. Если штатные тесты используют Testcontainers, не отключать их проверку БД ради экономии и не направлять их на рабочую/dev-базу с пользовательскими данными.
- Возможность выделенной переиспользуемой test-БД вводить осознанно; её тесты могут очищать данные, поэтому она не должна совпадать с dev/production.
- Перед контейнерным прогоном проверить наличие нужного образа и свободное место. Не включать Testcontainers reuse глобально без изоляции тестов и контроля очистки данных.
- Не выполнять prune и не удалять образы, контейнеры или тома автоматически. Новые объёмные скачивания и очистка — по отдельному согласованию.

## 9. Критерии завершения MVP

- Все шесть инструментов видны выбранному MCP-клиенту и выполняют описанный контракт.
- Любой вызов авторизован от конкретного пользователя; права совпадают с DoneIt UI.
- Можно создать, найти, прочитать, изменить и закрыть обычную задачу; после повторной отправки нет дубля.
- Не переданные в PATCH поля, теги, исполнители и фактическое время сохраняются. Изменения пользователя не перезаписываются молча.
- Регулярки и их статусы не меняются; физического удаления и массовых инструментов нет.
- Действия записаны в аудит; интерфейс DoneIt отражает реальные изменения.
- Подготовлено прямое HTTP-подключение ноутбук → VPS с токеном, имеющим конечный срок действия; без SSH. Фактическая проверка на VPS выполняется после отдельного поручения на доступ/deploy.
- Есть документация подключения, ротации ключа, ограничений подтверждения и отключения MCP. Веб-авторизация не сломана.

## 10. Ориентировочная оценка

5–8 рабочих дней для одного разработчика, включая тесты и подключение выбранного клиента: 1–2 дня на каркас/защиту, 1 день на чтение, 2–3 дня на запись/аудит/конкуренцию, 1–2 дня на проверки и подключение. Это оценка, а не срок обязательства; основной риск — авторизация и перенос контекста в выбранной версии Spring AI, а также совместимость клиента. HTTPS и полноценное серверное согласование в оценку не входят.
