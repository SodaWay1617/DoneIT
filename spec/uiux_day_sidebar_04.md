# DoneIt — ТЗ: правая колонка и календарная навигация

**Область:** страница «Сегодня», десктопная версия  
**Статус:** реализовано локально; проверка на реальном iPhone остаётся открытой.
**Тип задачи:** UI/UX-рефакторинг существующих компонентов  
**Приоритет:** следующий этап обновления интерфейса

## 1. Цель

Привести правую колонку страницы «Сегодня» к согласованному с референсом виду, сделать мини-календарь полноценным инструментом навигации по дням и убрать дублирующиеся элементы управления из верхней части страницы.

После доработки пользователь должен иметь возможность:

- Переключать день непосредственно через календарь.
- Видеть расписание задач выбранного дня.
- Использовать массовые и вспомогательные действия из компактной панели.
- Создавать обычную или регулярную задачу через одну точку входа.
- Работать с задачами без дублирования навигации и лишних элементов.

## 2. Границы изменений

**В рамках задачи:**
- Верхняя панель страницы «Сегодня».
- Правая колонка ПК-интерфейса.
- Мини-календарь и переход по датам.
- Блок расписания на день.
- Блок быстрых действий.
- Кнопка создания задачи.
- Адаптивное поведение изменяемых компонентов.

**Вне рамок задачи:**
- Переработка карточек задач и их контекстного меню.
- Изменение боковой навигации.
- Изменение структуры проектов и тегов.
- Изменение бизнес-логики регулярных задач.
- Редизайн полноценной страницы «Календарь».
- Создание нового механизма хранения задач.

## 3. Верхняя часть страницы

### 3.1. Удалить дублирующую навигацию по дням

В десктопной версии убрать из верхнего блока:

- Кнопку перехода на предыдущий день.
- Кнопку перехода на следующий день.
- Кнопку «Перейти к дате».

Эти элементы дублируют функциональность мини-календаря в правой колонке.

**Оставить:**
- Надпись «СЕГОДНЯ» для текущей даты либо соответствующее обозначение выбранного дня.
- Крупную дату.
- День недели.
- Кнопку «Создать задачу».
- Существующий блок статистики «Надо / Хочу / Можно / Активных задач».

Верхний блок должен стать компактнее и не содержать лишних управляющих элементов.

### 3.2. Единая кнопка создания

На ПК оставить одну основную кнопку «Создать задачу».

При нажатии открывать существующую форму создания задачи, предусматривающую выбор обычной или регулярной задачи.

Допустим вариант split-button с отдельной стрелкой, открывающей выбор типа задачи, если это проще интегрировать в текущую архитектуру.

**Не создавать вторую самостоятельную кнопку «Создать регулярную».**

### 3.3. Мобильная версия

На iPhone сохранить возможность перехода между днями через компактную навигацию, поскольку правая колонка на мобильном экране отсутствует.

- Предыдущий день.
- Выбор даты.
- Следующий день.

Не удалять эти элементы из мобильной версии при изменении десктопной.

## 4. Правая колонка ПК

### 4.1. Компоновка

Правая колонка должна содержать три блока в следующем порядке:

1. **Календарь**
2. **Расписание на день**
3. **Действия на день**

Отдельный фильтр «Планирование» над календарём не нужен: фильтрация уже предусмотрена в списке задач.

Использовать текущую палитру DoneIt: светлые молочные поверхности, бежевый фон, бирюзовые и приглушённые зелёные акценты.

Карточки должны иметь согласованные радиусы, внутренние отступы, границы и типографику.

### 4.2. Адаптивная ширина

Правая колонка должна занимать примерно 240–300 px в зависимости от доступной ширины.

Основной список задач имеет приоритет по ширине.

При недостатке горизонтального пространства не допускать сжатия календаря до нечитаемого состояния.

Рекомендуемое поведение:
- Широкий ПК: основной список и правая колонка.
- Узкий ПК / планшет: переход к одноколоночному расположению либо скрытие правой колонки с доступом к её функциям через существующие разделы.
- iPhone: отдельная правая колонка не отображается.

Точный breakpoint выбрать исходя из реальной ширины контента и проверить на нескольких размерах экрана.

## 5. Интерактивный мини-календарь

### 5.1. Внешний вид

Календарь должен содержать:

- Заголовок «Календарь».
- Название месяца и год.
- Стрелки переключения месяцев.
- Дни недели, начиная с понедельника.
- Сетку дат месяца.
- Выделение выбранной даты.
- Отличимое, но ненавязчивое обозначение реального сегодняшнего дня.

Использовать локализованные названия месяцев и дней недели.

### 5.2. Выбор дня

**Главное требование: клик по дате открывает соответствующий день в разделе «Сегодня».**

При выборе даты:

1. Обновляется выбранная дата.
2. Обновляется заголовок страницы.
3. Загружаются актуальные задачи выбранного дня.
4. Пересчитывается статистика выбранного дня.
5. Обновляется расписание справа.
6. Выделение в мини-календаре перемещается на выбранную дату.

Все элементы должны отображать одну и ту же выбранную дату.

Использовать существующий механизм открытия дня, а не создавать отдельную реализацию получения задач.

### 5.3. Переключение месяцев

Стрелки календаря изменяют **отображаемый месяц**, но сами по себе не изменяют выбранный день.

Например:
- Открыт день 24 октября.
- Пользователь переключает календарь на ноябрь.
- Список задач остаётся за 24 октября.
- Пользователь нажимает 12 ноября.
- Открывается 12 ноября.

Так исключаются неожиданные изменения контекста при просмотре календаря.

### 5.4. Состояния дат

Предусмотреть:

- Сегодняшняя дата.
- Выбранная дата.
- Обычная дата.
- Дата вне текущего месяца, если такие дни отображаются.
- Hover и focus.

Если выбранная дата одновременно является сегодняшней, использовать единое согласованное оформление.

Не полагаться только на цвет для обозначения выбранного дня.

### 5.5. Дополнительные требования

- Корректно обрабатывать переходы между годами.
- Учитывать високосные годы.
- Не сбрасывать фильтр выбранного проекта или тега при переключении даты.
- Не изменять даты самих задач при навигации.
- Поддерживать открытие даты через URL, если такой механизм уже предусмотрен.
- Сохранять корректную работу кнопок браузера «Назад» и «Вперёд».

## 6. Блок «Расписание на день»

### 6.1. Назначение

Компактно показывать задачи выбранного дня, у которых указано точное время начала.

Это обзор, а не полноценный редактор расписания.

### 6.2. Состав строки

Каждая запись содержит:

- Время начала.
- Название задачи.
- Оценку длительности, если она указана.
- Небольшой цветовой маркер.

Например:

**09:00 — Зарядка**  
15 мин

**10:30 — Учёт финансов**  
30 мин

**12:00 — Рефакторинг**  
3 ч 20 мин

### 6.3. Логика отображения

- Показывать задачи выбранного дня, имеющие точное время.
- Сортировать по времени начала по возрастанию.
- Если есть оценка длительности, можно показывать интервал начала и окончания.
- Если оценки нет, показывать только время начала.
- Не придумывать время начала для задач без точного времени.
- Не выводить отдельные экземпляры одной задачи только из-за наличия дедлайна.
- Соблюдать существующую логику отображения регулярных задач.

Клик по записи открывает карточку соответствующей задачи.

### 6.4. Пустое состояние

Если задач с точным временем нет, показывать компактное сообщение:

«На этот день нет задач с указанным временем».

Не оставлять пустую карточку без объяснения.

### 6.5. Ограничение высоты

Если задач много, блок не должен бесконтрольно увеличивать высоту страницы.

Можно использовать ограничение высоты с внутренней прокруткой или компактное раскрытие полного списка.

## 7. Блок «Действия на день»

### 7.1. Состав

Оставить три существующих действия:

1. **Перенести незавершённые на завтра**
2. **Перенести просроченные на сегодня**
3. **Выбрать случайную задачу**

Убрать отдельную кнопку «Создать регулярную».

Создание регулярной задачи должно быть доступно из общей кнопки создания задачи.

### 7.2. Внешний вид

Каждое действие оформляется как компактная строка с иконкой и текстом.

Не использовать большие кнопки, занимающие чрезмерную высоту.

Действия должны визуально отличаться от списка задач, но не конкурировать с основной кнопкой создания.

### 7.3. Поведение

Сохранить существующую бизнес-логику каждого действия.

Для массового переноса задач предусмотреть подтверждение с количеством затрагиваемых задач, если подтверждение ещё не реализовано.

Например:

«Перенести 4 незавершённые задачи на завтра?»

Не выполнять массовые изменения при случайном нажатии.

### 7.4. Контекст выбранной даты

При открытии исторической или будущей даты действия должны оставаться логически корректными.

Важно не подменять фактическое «сегодня» выбранной пользователем датой без явного решения.

Рекомендуется:

- «Перенести незавершённые на завтра» — относительно выбранного дня, с понятным подтверждением дат.
- «Перенести просроченные на сегодня» — относительно реальной текущей даты, как и предполагает название.
- «Выбрать случайную задачу» — использовать существующую область выбора.

Если действующая бизнес-логика отличается, сохранить её и отразить корректный смысл действия в интерфейсе.

## 8. Согласованность состояния

Верхний блок, список задач, мини-календарь и расписание должны использовать единый контекст выбранной даты.

При изменении даты не должно возникать ситуации, когда:

- Заголовок показывает 24 октября.
- Календарь выделяет 25 октября.
- Расписание загружено за 23 октября.

То же касается активных фильтров проекта и тегов.

Предпочтительно использовать существующие параметры запроса и механизмы серверного рендеринга Thymeleaf, если они уже решают эту задачу.

**Не вводить новый frontend-фреймворк ради данного этапа.**

## 9. Локализация

В DoneIt уже есть переключение русского и английского языков.

Все новые и изменённые пользовательские строки должны использовать существующую систему локализации.

Не создавать отдельную систему переводов и не зашивать русские строки непосредственно в компоненты.

Это касается названий месяцев, дней недели, пустых состояний, подтверждений и подсказок.

## Решения реализации — 24 октября 2026

- На ширине от 1200 CSS px правая колонка имеет ширину 260 px, а дублирующая навигация по дням в заголовке скрыта. Ниже 1200 px остаются верхние переходы и выбор даты, календарь и мини-расписание скрыты, действия расположены после списка. Боковая и нижняя навигация не перерабатывались.
- Параметр `navMonth` управляет только отображаемым месяцем. Выбранный день по-прежнему открывается через `/tasks?date=...`. Для сетки дат переиспользован `TaskApplicationService.getCalendarMonth`, включая понедельник, високосные годы и границы месяцев. Проект, категория и личные теги сохраняются без дублирования параметров.
- Мини-расписание показывает актуальные задачи того же контекста, что и список, с точным стартом на выбранный день. Просроченный старт из другого дня туда не подставляется. Регулярки берутся из выбранного вхождения; дедлайн не создаёт вторую запись. Порядок — по времени, ограничение высоты — 360 px с прокруткой.
- Создание на ПК — split-button: основная часть открывает существующую форму обычной задачи, стрелка — выбор типа. На телефоне плюс открывает тот же выбор обычной/регулярной задачи. Отдельной кнопки создания регулярки в действиях больше нет.
- Бизнес-логика массовых действий сохранена. Первый перенос сдвигает каждую подходящую обычную задачу на один день от её собственной даты, если план не позже выбранного дня; он НЕ назначает всем одну дату завтра. Поэтому кнопка переименована в «Сдвинуть незавершённые на день», а подтверждение объясняет реальные даты.
- Массовые переносы по-прежнему охватывают все проекты и задачи, за которые отвечает пользователь, независимо от фильтров списка. Задачи «Можно», регулярки, задачи без плановой даты и неактивные статусы не затрагиваются. Второе действие использует реальное сегодня; случайная задача выбирается из прежней области обычных актуальных задач реального сегодняшнего дня.
- Перед подтверждением выполняется защищённый GET `/api/tasks/bulk-preview?date=...` с `Cache-Control: no-store`. Счётчик использует тот же SQL-предикат, что и UPDATE. Он актуален на момент предварительного запроса, не блокирует параллельную работу другого устройства. При сбое запроса, смене пользователя или отмене POST не отправляется. Затем существующий механизм обновляет CSRF для восстановления запомненного входа.
- Новая схема БД, доменные статусы и отдельный frontend-фреймворк не добавлялись.
