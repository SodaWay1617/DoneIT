# DoneIt — UI/UX Specification 03
## Компактный список актуальных задач

**Статус:** реализовано; проверка на реальном iPhone остаётся открытой  
**Область:** страница «Сегодня», список задач, фильтрация, быстрые действия  
**Референс:** последнее утверждённое изображение Desktop + iPhone  
**Технологии:** существующий стек DoneIt, Thymeleaf, CSS, JavaScript

---

## 1. Контекст и цель

В DoneIt уже реализованы:

- Боковая и мобильная навигация.
- Проекты и общие задачи.
- Статусы и приоритеты.
- Категории планирования.
- Учёт и оценка времени.
- Регулярные задачи.
- Подзадачи.
- Теги (если соответствующая функциональность уже существует в коде).
- Несколько представлений задач.

Текущий список использует крупные карточки с большим количеством кнопок и элементов управления.

Это создаёт проблемы:

1. На экране помещается слишком мало задач.
2. Часто используемая информация смешивается с редкими действиями.
3. Одни и те же элементы управления повторяются в каждой карточке.
4. Мобильная версия требует чрезмерной прокрутки.
5. Визуальная иерархия задач недостаточно выражена.

### Целевой результат

Создать компактный список, в котором:

- Задачи легко просматривать и сравнивать.
- Основная информация видна без открытия карточки.
- Все подробности доступны по нажатию на задачу.
- Быстрые действия доступны через контекстное меню.
- Завершение задачи доступно непосредственно из списка через чекбокс.
- Desktop и Mobile используют единую бизнес-логику.

**Важно:** референс определяет визуальное направление, но не является точным техническим макетом. Приоритет имеют требования спецификации, корректность поведения и существующая дизайн-система.

## 2. Область изменений

Переработать:

1. Контейнер списка «Актуальные задачи».
2. Компактное отображение отдельной задачи.
3. Отображение приоритета, проекта, тегов и времени.
4. Панель фильтрации задач.
5. Контекстное меню быстрых действий.
6. Механизм завершения через чекбокс.
7. Адаптивную мобильную версию.
8. Пустые состояния списка.

Не перерабатывать:

- Sidebar.
- Мобильную нижнюю навигацию.
- Заголовок страницы и управление датой.
- Панель дневной статистики.
- Страницы Inbox и Backlog.
- Kanban и Calendar.
- Полную форму редактирования задачи.
- Существующую бизнес-логику задач.

## 3. Состав страницы «Сегодня»

На странице остаются:

1. Заголовок с выбранной датой.
2. Сводка дневной нагрузки.
3. Список актуальных задач.
4. Существующие дополнительные виджеты и действия на день, если они не противоречат новой компоновке.

### 3.1. Состав списка

В основном списке должны находиться только актуальные задачи выбранного дня согласно существующим правилам отбора.

Не выводить отдельными секциями:

- Входящие.
- Бэклог.
- Выполненные задачи.
- Закрытые задачи.

Для этих задач уже предусмотрены самостоятельные разделы навигации.

Не изменять правила попадания задач в список без необходимости.

### 3.2. Расположение

**Desktop:**

- Список занимает основную широкую колонку.
- В правой колонке сохраняются существующие вспомогательные элементы.
- Основной список визуально доминирует над вспомогательными виджетами.

**Mobile:**

- Список занимает всю доступную ширину.
- Не возникает горизонтального скролла.
- Нижняя навигация остаётся доступной.
- Задачи не перекрываются системными элементами iOS.

---

## 4. Компактная строка задачи

### 4.1. Общая структура

Каждая задача отображается отдельной компактной строкой внутри общего контейнера.

Строки разделяются тонкими линиями.

Не использовать крупные самостоятельные карточки с большими отступами.

**Desktop:**

- Слева — квадратный чекбокс.
- По центру — название и метаданные задачи.
- Справа — оценка времени и временной интервал либо дата.
- Вся основная область строки кликабельна.

**Mobile:**

- Слева — квадратный чекбокс.
- Справа от него — название и метаданные.
- Время и дата располагаются компактно под названием или в отдельной строке.
- Содержимое адаптируется к доступной ширине.

### 4.2. Название

Название является главным текстовым элементом задачи.

Требования:

- Использовать полужирное начертание.
- Не обрезать название без возможности увидеть его целиком.
- Для длинных названий допускать перенос на вторую строку.
- При необходимости показывать полное название в карточке редактирования.
- Не отображать полное описание непосредственно в списке.

Название должно оставаться визуально важнее тегов, проекта и статуса.

### 4.3. Проект

Показывать принадлежность задачи к проекту.

Использовать компактный бейдж с иконкой и названием.

Примеры:

- Домашние дела.
- Авто.
- Финансы.
- Работа.

Проект — это отдельная сущность, не путать с тегом.

В Desktop и Mobile использовать одинаковую семантику отображения.

### 4.4. Теги

Предусмотреть отображение тегов задачи.

Пример:

**Зарядка**  
`#Prime` · `Здоровье`

Здесь:

- `#Prime` — тег.
- `Здоровье` — проект.

Требования:

- Одна задача может иметь несколько тегов.
- Отображать теги компактными бейджами.
- Не смешивать теги и проекты в одну сущность.
- Использовать различимые визуальные стили.
- Если тегов много, не допускать чрезмерного увеличения высоты строки.

На Desktop можно показывать несколько тегов с индикатором дополнительных.

На Mobile допустимо ограничить количество видимых тегов и показать `+N`.

Полный список тегов доступен в карточке задачи.

Если backend-теги ещё не реализованы, сначала проверить существующую модель и согласовать минимально необходимое расширение. Не создавать отдельную параллельную систему тегов исключительно для UI.

### 4.5. Приоритеты

**Обязательно вернуть отображение приоритетов.**

Поддержать все существующие значения:

- Нет.
- Низкий.
- Нормальный (средний).
- Высокий.
- Критический.

Использовать компактные цветовые бейджи.

Предлагаемая палитра:

| Приоритет | Отображение |
|---|---|
| Нет | Бейдж не показывать |
| Низкий | Нейтральный голубой или серо-бирюзовый |
| Нормальный | Мягкий песочный |
| Высокий | Оранжевый |
| Критический | Красный |

Не использовать цвет как единственный способ различения приоритета: текст должен оставаться читаемым.

Приоритеты должны сохранять текущие названия и значения в доменной модели.

### 4.6. Статусы

Существующие статусы не изменять.

В компактном списке допускается не отображать статус каждой задачи, если он не несёт дополнительной полезной информации.

Однако состояния, требующие внимания, например просрочка, должны оставаться заметными.

Не заменять существующие статусы приоритетами или тегами.

## 5. Время и интервалы

### 5.1. Задача с точным временем и оценкой

Если у задачи есть:

- Дата планирования.
- Точное время начала.
- Оценка продолжительности.

Отображать рассчитанный интервал.

Пример:

**Рефакторинг**  
Оценка: 3 ч 20 мин  
Интервал: 09:00–12:20

Конец интервала рассчитывается как:

`plannedStartAt + estimatedDuration`

Не сохранять рассчитанное время окончания как отдельное поле без необходимости.

Использовать существующую временную модель и правила приложения.

### 5.2. Задача с точным временем без оценки

Показывать только время начала.

Пример:

**Зарядка**  
09:00

Не придумывать продолжительность.

### 5.3. Задача с оценкой, но без точного времени

Показывать оценку продолжительности без интервала.

Пример:

**Починить ванную**  
Оценка: 2 ч  
Без точного времени

Такая задача должна оставаться полноценной строкой списка.

### 5.4. Задача без оценки и точного времени

Показывать дату, если она информативна, либо не занимать место пустым полем.

Не выводить технические значения `null`, `00:00` или фиктивные интервалы.

### 5.5. Важные ограничения

- Оценка времени не равна фактически затраченному времени.
- Интервал отображения не означает бронирование времени в расписании, если такой логики нет.
- Пересечение интервалов разных задач не должно автоматически изменять их даты.
- Не изменять существующие правила расчёта дневной нагрузки.
- Для регулярных задач использовать данные конкретного вхождения, если так устроена текущая модель.

## 6. Чекбокс завершения задачи

### 6.1. Внешний вид

Заменить круглые декоративные элементы слева от задач на квадратные чекбоксы.

Состояния:

- Не выполнена — пустой квадрат.
- Выполнена — квадрат с галочкой.

Чекбокс должен быть хорошо различим и иметь удобную область нажатия.

### 6.2. Поведение

Нажатие на чекбокс запускает существующий сценарий завершения задачи.

Не открывает форму редактирования.

Не запускает контекстное меню.

Не вызывает одновременно несколько действий.

### 6.3. Учёт времени при завершении

В DoneIt уже существует сценарий записи затраченного времени при завершении.

Его необходимо сохранить.

Если при переводе в DONE приложение предлагает указать фактически затраченное время, нажатие на чекбокс должно запускать этот же сценарий.

Не обходить существующую бизнес-логику прямой сменой статуса.

### 6.4. Регулярные задачи

Для регулярной задачи чекбокс завершает конкретное вхождение за выбранный день.

Не завершать всю регулярную серию.

Использовать существующий механизм выполнения регулярных задач.

### 6.5. После завершения

После успешного завершения задача должна исчезнуть из списка актуальных задач, если это соответствует существующим правилам.

Количество активных задач и дневная статистика должны обновиться.

При ошибке сохранять исходное состояние чекбокса и показывать понятное сообщение.

---

## 7. Открытие задачи

### Desktop

Обычный клик левой кнопкой мыши по основной области строки открывает существующую страницу редактирования задачи.

Не создавать новую карточку или дополнительную форму просмотра.

### Mobile

Короткое нажатие по строке открывает ту же страницу задачи.

### Исключения

Не запускать переход при взаимодействии с:

- Чекбоксом.
- Контекстным меню.
- Кнопками внутри контекстного меню.
- Другими интерактивными элементами.

Не допускать двойной отправки действий.

---

## 8. Контекстное меню быстрых действий

### 8.1. Desktop

Нажатие правой кнопкой мыши на задачу открывает компактное контекстное меню.

Меню появляется рядом с выбранной строкой, предпочтительно над ней, как на референсе.

Если сверху недостаточно места, допускается размещение снизу.

Не допускать выхода меню за границы экрана.

### 8.2. Mobile

Длительное нажатие на задачу открывает то же контекстное меню.

Короткое нажатие по-прежнему открывает карточку задачи.

Длительное нажатие не должно одновременно вызывать переход в карточку.

Предусмотреть удобное позиционирование меню на iPhone, чтобы оно не перекрывалось нижней навигацией.

### 8.3. Состав меню

Для обычной задачи — ровно пять основных действий:

1. **Записать время** — иконка часов.
2. **Перенести** — иконка календаря.
3. **Редактировать** — иконка карандаша.
4. **Выполнить** — иконка галочки.
5. **Закрыть** — иконка закрытия.

Не добавлять в меню дополнительные действия на этом этапе.

Уточнение пользователя для регулярных задач: меню содержит только «Записать время», «Редактировать», «Выполнить сегодня» и «Пропустить сегодня». Чекбокс и «Выполнить сегодня» отмечают вхождение за выбранную дату, а не завершают серию. Пропуск доступен только для сегодняшнего дня согласно существующей серверной логике. Выполнение и закрытие всей серии остаются в полной карточке регулярной задачи.

### 8.4. Записать время

Открывает существующий сценарий записи фактически затраченного времени.

Не переводит задачу автоматически в DONE.

После сохранения обновляет отображаемые данные, если они затрагиваются.

### 8.5. Перенести

Открывает небольшое модальное окно выбора новой даты.

Окно содержит:

- Заголовок «Перенести задачу».
- Текущую дату планирования.
- Выбор новой даты.
- Кнопки «Перенести» и «Отмена».

При переносе:

- Использовать существующий механизм изменения даты.
- Сохранять точное время, если оно задано и пользователь не меняет его отдельно.
- Не менять deadline.
- Не менять статус, приоритет, проект или теги.
- Для регулярной задачи отдельный перенос вхождения не добавляется: изменение расписания серии остаётся в полной карточке, а действия «Перенести» в её быстром меню нет.

После успешного переноса обновить список.

Если задача больше не относится к выбранному дню, она должна исчезнуть из текущего списка.

### 8.6. Редактировать

Открывает существующую форму редактирования задачи.

Поведение идентично обычному клику по строке.

### 8.7. Выполнить

Запускает тот же сценарий, что и чекбокс завершения.

Не реализовывать отдельную логику завершения.

### 8.8. Закрыть

Переводит задачу в существующий статус CLOSED через действующий механизм.

Это отмена задачи, а не успешное выполнение.

Если текущий сценарий требует подтверждения, сохранить его.

### 8.9. Закрытие меню

Меню закрывается:

- По клику вне меню.
- По Escape.
- После успешного действия.
- При переходе на другую страницу.
- При открытии меню другой задачи.

Одновременно может быть открыто только одно контекстное меню.

### 8.10. Доступность

Не делать правый клик и долгое нажатие единственными способами вызова меню.

Предусмотреть альтернативный способ открытия для клавиатуры, сенсорных устройств и пользователей, которым сложно выполнить длительное нажатие.

Допустимый вариант — небольшая кнопка дополнительных действий, появляющаяся при фокусе или наведении на Desktop и доступная на Mobile.

Не превращать эту кнопку в постоянную группу из пяти действий.

## 9. Фильтрация списка

### 9.1. Общая структура

В верхней части контейнера «Актуальные задачи» разместить компактную панель фильтров.

Фильтры не должны занимать несколько крупных строк на Desktop.

### 9.2. Категории планирования

Предусмотреть переключатели:

- Все.
- Надо.
- Хочу.
- Можно.

Использовать существующие категории приложения.

Рядом с категориями допускается отображать количество задач.

Количество должно рассчитываться по реальным данным текущего дня и контекста фильтрации.

### 9.3. Проекты

**Не создавать независимую систему фильтрации проектов.**

В Sidebar уже реализован выбор проекта.

Список должен учитывать выбранный проект из общего состояния навигации.

Если в референсе присутствует дополнительный селектор «Все проекты», не копировать его без необходимости.

Единый источник состояния фильтрации проектов обязателен.

### 9.4. Теги

Добавить фильтр по тегам.

Требования:

- Возможность выбрать один или несколько тегов.
- Возможность сбросить фильтр.
- Возможность показать все задачи.
- Фильтрация должна сочетаться с выбранным проектом и категорией планирования.

Предлагаемая семантика:

- Между проектом, категорией и тегами — AND.
- При выборе нескольких тегов — OR внутри группы тегов.

Например:

Проект «Здоровье» + категория «Надо» + тег `#Prime` показывает задачи, удовлетворяющие всем трём условиям.

Если текущая модель тегов предполагает другую семантику, сохранить её и не создавать противоречащие правила.

### 9.5. Mobile

На мобильном экране не выводить длинную панель фильтров.

Использовать компактную кнопку фильтрации, открывающую панель или модальное окно.

Внутри доступны:

- Категория планирования.
- Теги.
- Сброс дополнительных фильтров.

Проект по-прежнему определяется общей навигацией.

Активные фильтры должны быть визуально заметны.

## 10. Сортировка

Сохранить существующие правила сортировки и пользовательские настройки, если они уже реализованы.

Предусмотреть сортировку по:

- Приоритету.
- Наличию точного времени.
- Времени начала.
- Статусу.
- Названию.

Не изменять правила сортировки скрыто в рамках визуального редизайна.

Если текущая сортировка фиксированная, использовать её до отдельного согласования пользовательского управления сортировкой.

Приоритетные и просроченные задачи должны оставаться визуально различимыми независимо от порядка.

## 11. Mobile и iPhone PWA

### 11.1. Компактность

Мобильная строка содержит:

- Чекбокс.
- Название.
- Проект.
- Основные теги.
- Приоритет.
- Оценку и/или время.

Стараться укладывать обычную задачу в 2–3 содержательные строки.

Длинные названия и дополнительные теги могут увеличивать высоту строки.

Не устанавливать жёсткую высоту, которая обрезает содержимое.

### 11.2. Жесты

- Короткое нажатие — открыть задачу.
- Длительное нажатие — открыть меню действий.
- Нажатие на чекбокс — выполнить задачу.

Обязательно проверить отсутствие конфликтов между этими взаимодействиями.

### 11.3. Контекстное меню

На iPhone меню должно быть удобным для касания.

Минимальная рекомендуемая область интерактивного элемента — около 44×44 CSS px.

Не размещать пять слишком маленьких иконок вплотную друг к другу.

Уточнение пользователя: на мобильном экране меню остаётся в один ряд, только иконки без видимого текста. Размер кнопок — минимум 44×44 CSS px. Для скринридера сохраняются названия действий, для наведения — подсказки. На Desktop иконки сопровождаются подписями.

Семантика действий должна быть одинаковой с Desktop.

### 11.4. Особенности PWA

Проверить:

- Safari на iPhone.
- Установленное PWA.
- Safe Area.
- Нижнюю навигацию.
- Прокрутку страницы.
- Открытие модальных окон.
- Длительное нажатие без случайного выделения текста.
- Отсутствие нежелательного системного контекстного меню поверх собственного.

Не блокировать стандартные жесты браузера глобально.

## 12. Визуальный стиль

Использовать существующую дизайн-систему DoneIt.

Сохранить:

- Светлый бежевый фон.
- Тёплые нейтральные поверхности.
- Бирюзовый как основной акцент.
- Скруглённые контейнеры.
- Тонкие разделители.
- Спокойную типографику.

### Визуальная иерархия

1. Название задачи.
2. Время и оценка.
3. Приоритет.
4. Проект и теги.
5. Второстепенные сведения.

Не превращать все метаданные в одинаково яркие бейджи.

Не перегружать список иконками.

Не использовать декоративные элементы без функционального назначения.

### Плотность

Ориентир для Desktop — отображение примерно 8–12 компактных задач в основной рабочей области при типичном разрешении 1920×1080, с учётом высоты заголовка и статистики.

Это ориентир, а не требование фиксированной высоты строк.

На Mobile приоритет — читаемость и удобство касаний, а не максимальная плотность любой ценой.

## 13. Технические требования

Перед реализацией агент должен изучить:

- Текущий шаблон страницы «Сегодня».
- Существующие Thymeleaf fragments задач.
- CSS и JavaScript.
- Модель задачи.
- Проекты и механизм общей фильтрации.
- Теги и их хранение.
- Приоритеты.
- Механизм выполнения.
- Регулярные задачи.
- Учёт времени.
- Механизм переноса.
- Локализацию RU/EN.

### Принципы

- Использовать существующие backend-операции.
- Не дублировать бизнес-логику в JavaScript.
- Не создавать новые endpoint'ы, если существующие подходят.
- Не переписывать модель задач ради отображения.
- Не внедрять новый frontend-фреймворк.
- Выделять переиспользуемые UI-компоненты.
- Избегать inline-стилей и дублирования CSS.
- Сохранять защиту изменяющих запросов, включая CSRF.
- Не нарушать доступ к задачам общих проектов.
- Использовать существующие ключи локализации и добавлять новые для RU/EN.

Если обнаружена необходимость изменения backend, сначала определить минимальный объём и влияние на существующие представления.

## 15. Сценарии проверки

### Сценарий A — Обычная задача

Пользователь открывает страницу «Сегодня».

Видит компактную строку задачи с названием, проектом, приоритетом и оценкой.

Нажимает на строку.

Открывается существующая форма редактирования.

### Сценарий B — Быстрое выполнение

Пользователь нажимает на квадратный чекбокс.

Запускается существующий сценарий завершения задачи.

После успешного выполнения задача исчезает из актуального списка.

Статистика обновляется.

### Сценарий C — Контекстное меню

Пользователь нажимает правой кнопкой на задачу.

Появляется меню из пяти действий.

Пользователь выбирает «Записать время».

Открывается существующий интерфейс учёта времени.

### Сценарий D — Перенос

Пользователь открывает меню задачи.

Выбирает «Перенести».

Указывает завтрашнюю дату.

После подтверждения задача переносится с сохранением остальных данных.

### Сценарий E — Теги

Пользователь выбирает тег `#Prime`.

В списке остаются только подходящие задачи с учётом выбранного проекта и категории.

После сброса фильтра отображается исходный список.

### Сценарий F — iPhone

Пользователь открывает DoneIt как установленное PWA.

Коротким нажатием открывает задачу.

Возвращается назад.

Длительным нажатием открывает меню действий.

Выполняет задачу через чекбокс.

Все действия работают без конфликтов с системными жестами iOS.

## 17. Definition of Done

Разработка считается завершённой, когда:

1. Список стал компактным и визуально согласованным с референсом.
2. Все существующие возможности работы с задачами сохранены.
3. Быстрые действия работают через контекстное меню.
4. Чекбокс завершает задачи корректно.
5. Проекты, теги и приоритеты отображаются без путаницы.
6. Временные интервалы рассчитываются корректно.
7. Desktop и iPhone PWA работают стабильно.
8. Изменения не затрагивают другие разделы приложения без необходимости.

**Главный критерий качества:** пользователь может быстро просмотреть десятки задач, открыть любую из них и выполнить основные действия без перегруженного интерфейса.

## Результат реализации — 24 октября 2026

- Текущая сортировка обычных и регулярных задач сохранена. Учитываются прежние серверные права доступа и выбранный в навигации проект.
- Категории считаются внутри контекста проекта и личных тегов. Фильтр тегов ограничивает дневной список, не меняя прежнюю семантику сводки нагрузки.
- Завершение, списания времени, пропуск и перенос используют существующие серверные операции с обновлением CSRF. После успешного действия страница загружается заново с сохранением фильтров; при ошибке выполнения ложная галочка не ставится.
- Визуально показаны два тега и счётчик остальных, полный набор — в карточке. Интервал использует явно заданный конец либо оценку от старта; ночь и длительности больше суток отмечаются отдельно.
- Проверки: 292 теста, успешная сборка JAR, сквозные сценарии Chromium и WebKit на ширинах 320–1440 px, включая ошибки и восстановление remember-me при выполнении регулярки за прошлый и текущий день.
- Реальный iPhone Safari, установленный PWA, системная клавиатура и реальные safe area требуют проверки на устройстве. Вёрстка и жесты проверены только в локальных браузерных движках; критерий реального iPhone пока не закрыт.
